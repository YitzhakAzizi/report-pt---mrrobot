# BUSINESS RULES

## Core Rule

The application exists to help users gain control over their money.

Every calculation, recommendation and feature should support this goal.

---

# Monthly Cycle

Every month starts with income.

The user first enters all income sources.

Income is always entered as NET salary.

Multiple income sources are supported for every person.

---

# Fixed Expenses

Fixed expenses are saved between months.

Users may edit them at any time.

They are automatically included in every new month.

---

# Variable Spending

The application does NOT require users to enter every purchase.

Instead, it calculates a monthly spending budget.

The user manages the monthly budget independently.

---

# Remaining Money

Remaining Money =

Total Income

minus

Fixed Expenses

The remaining amount becomes available for allocation.

---

# Allocation

The remaining money is allocated between:

- Daily spending
- Financial goals
- Emergency fund
- Investments
- Maaser
- Dreams

The application recommends.

The user decides.

---

# Maaser

Maaser is calculated from NET income.

The user may disable the Maaser feature.

The user may split Maaser between multiple organizations.

---

# Financial Goals

Goals are accumulated over time.

Progress is displayed visually.

Completed goals are marked as completed.

---

# Emergency Fund

Emergency fund is calculated according to predefined living expenses.

---

# Monthly Closing

Every month can be saved as history.

History represents a snapshot of that month.

History should not change unless the user explicitly chooses to reopen it.

---

# Recovery Mode

The application supports two financial modes.

Control Mode

For users whose income exceeds expenses.

Recovery Mode

For users who need to regain financial control before moving to Control Mode.

---

# Decision Principle

The application recommends.

The user always makes the final decision.

---

# Simplicity Rule

Users should never be required to track every transaction.

The application should reduce financial complexity.

Not increase it.

---

# Future Features

Future features must follow these principles.

If a feature increases complexity without providing meaningful value, it should be redesigned before implementation.
